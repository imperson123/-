# 版本对比：交付版 vs 新版引擎（以及 HAP 的三次演进）

> 用途：答辩问答（"你们迭代了什么？为什么用这一版？"）、复赛后规划。数据均来自本项目实测，未测项如实标注。

## 一、引擎版本对比（两条 T-MAC 引擎线）

| 维度 | **提交版引擎（旧 fork，kaleid-liner 基线）** | **新版引擎（202504_tmac，已修复，未集成）** |
|---|---|---|
| 底座 | 老 llama.cpp（ggml 单库时代），T-MAC 移植成熟 | 2025-04 现代底座（ggml 后端拆分后架构），T-MAC 移植为上游 WIP |
| 量化/scale 方案 | 每 **256** 权重 1 个 scale（kcfg + 预生成 tuned 内核） | 每 **64** 权重 1 个 scale（per-group、无 zero point） |
| 数值正确性 | ✅ 交付版输出正常（已三方验证） | ✅ **本项目修复后正常**（此前内核分发表缺 6 条路由 → 空转 → 输出 `is is is`） |
| 吞吐（同机 PC/WSL） | **25.10 tokens/s** | 18.66–20.37 tokens/s（-t 4 / -t 8；宿主带载） |
| 吞吐（鸿蒙设备） | 模拟器 **23.35** / 真机 **20.39** tokens/s | 未上设备（未集成 prebuilt） |
| 内核级基准 | 7.1 µs（x86 AVX2）/ **7.8 µs**（arm64 NEON） | 未测 |
| 内存（真机峰值） | 1413.6 MB（hidumper 交叉核验 1393 MB） | 未测（模型体积同量级） |
| 成熟度 | 冻结但完整：kcfg 已 tuned、交付链路全通 | 上游 WIP：数值已由我们修好，**kcfg 未调优** |
| 生态与维护 | 老底座，跟进上游困难 | ✨ 现代底座，易跟进上游（长期价值） |
| 集成成本 | 0（已在交付包内） | 需重建双 ABI prebuilt + App 接线 + 重新三闸门验证（约 4–6 h） |
| **结论** | **提交采用**（更快 + 已验） | **复赛后主线**：数值修复已入仓（补丁 `ohos/patches/`），下一步调优（kcfg 内核调优 + 128 组量化变体） |

### 关键澄清（答辩口径）

1. **新版此前"46.93 tokens/s"是伪速度**：分发表缺路由 → 内核空转（等于跳过矩阵乘）→ 又快又错。修复后真实速度 **18.66–20.37**，**不高于**旧版 25.10。
2. **修复是真实成果**：定位到上游 WIP 的数值缺口（`get_scales_size` 支持三种口径，而分发表只覆盖两种极端且无兜底），补 6 条路由后输出恢复正常（WSL 复现 ×2）。补丁已入仓，可直接套用/回馈上游。
3. **两版共用同一套思想与验证方法**（LUT 查表内核 + 链式 KV 记忆调度 + L2 感知调度），差别在底座与 scale 粒度——所以"旧版更快"是工程调优的差距，不是技术路线差异。

## 二、交付 HAP 的三次演进（同一路线，逐轮加固）

| 构建 | 时间 | 关键变化 | 效果 | SHA256（前 12 位） |

> ②是性能数据的来源版本；③只改采样策略，**对吞吐口径影响 <0.5%**（采样耗时 0.44 ms/token），因此性能数据无需重测。
> 三次演进都保持 **同一签名**（debug 自动签名，UDID 白名单 = 本队手机 + 官方模拟器 ✓ 有效期至 2026-10-13）。

## 三、一句话总结

**"新版不是更好，只是更新的底座；旧版不是更旧，只是调得更透。"**
提交用旧版（更快、已验、交付链全通）；新版作为复赛后的可维护升级路径，其最大障碍（上游数值缺口）已由本项目排除。
