# 技术核心总纲（LUT-SA / 鸿蒙玲珑核）

> 用途：作品说明文档「技术方案」章节、PPT、答辩。所有数字均来自本项目实测；未测项如实标注。
> 引用口径：模拟器 = 官方模拟器 Pura X View（HarmonyOS 7.0.0 / x86_64 / 4 vCPU）；真机 = HUAWEI Pura 70 Pro（HBN-AL00 / API 24 / arm64-v8a），均为**交付版 HAP**。

## 0. 一页速览

**一句话**：面向端侧大模型**首字响应（TTFT）的系统级加速**——用 2.44 BPW 比特级查表（LUT）内核替代"反量化 + 浮点乘加"，再叠加**端侧记忆调度**（链式 KV 跨轮复用）与**感知调度**（前后台释放/预热闭环），全程用户态、不改 OS 内核。

| 技术核心 | 机制 | 关键数字 |
|---|---|---|
| ① LUT 计算内核 | 权重比特直接当表下标，查表 + 整数累加 | 内核 **7.1 µs（x86 AVX2）/ 7.8 µs（arm64 NEON）**；vs 反量化 **2.5–5.9×** |
| ② 端侧记忆调度 | 跨轮 KV 记忆链 + 最长公共前缀复用 + 分歧裁剪 | TTFT **240 ms → 0.57/1.15 ms（216×）**；部分复用 **6 of 13** |
| ③ 感知调度 | 前后台感知 → 引擎释放/预热，60 s 滞回 | 后台释放 **1.30 GB**（Pss 1370→71 MB）；对照组 0 |
| ④ 交付形态 | HAP（应用级）+ SA 预研（系统服务化） | 真机三闸门 + 离线验签；SA qemu 全链路 PASS |
| ⑤ 输出质量工程 | 重复惩罚 1.15/64 + 真 top-p 0.95 | 同提示 A/B：复读 → 通顺零复读 |

## 1. 问题定义与路线选择

**痛点**：主流低比特推理在计算前必须把 2~4 bit 权重**反量化回高精度**再做浮点乘加——访存与类型转换开销抵消了低比特的带宽收益；端侧多任务并发下首字延迟与能耗进一步劣化。

**路线**：T-MAC 式**查表（LUT）范式**——把"权重比特组合 × 激活"的乘积**预先算好存表**，推理时权重比特**直接作为表下标**，一次查表 + 一次整数累加，从算子层消除整条反量化路径。**不改变模型精度**（同一份量化权重，只换计算路径），只改变快慢与内存足迹。

**为什么在操作系统赛道**：性能收益来自"算子层（内核）+ 系统层（记忆/感知调度）"的耦合设计，而非调用现成框架——正好落在赛题"提升系统 AI 任务运行效率 / 端测记忆调度 / 感知数据流处理"的口径上。

## 2. 技术核心 ①：LUT 计算内核

### 2.1 原理（五项）

1. **查表替代乘加**：以一组低比特权重（8 个 2-bit 权重 = 16 种组合/4 值域）为索引，其与激活点积的结果仅有有限种，推理前用 int8 激活预计算查找表；推理时权重比特直接作为表下标，一次查表 + 一次整数累加替代"反量化 + 乘加"整条路径。
2. **比特交织布局**：权重离线转换为比特平面交织格式，一组权重的比特可直接拼成查表索引，消除运行期位运算开销。
3. **SIMD 向量化**：查表用 TBL 类指令（NEON）/ pshufb（AVX2），累加走整数 SIMD；按缓存行对齐表布局、顺序访存，硬件预取友好。
4. **多线程分块**：输出通道维切块分发至多核，线程数由调度层动态给定；数据只读共享、无线程间写竞争。
5. **内核形态与配置**：按 **m128-k3200** 形状分块（一次处理 128 个输出通道 × 3200 输入维），8 权重一组的组合查表（2-bit×8 → 256 项 int8 查找表）；内核配置（kcfg）内嵌于产物，运行时无外部配置依赖。支持 1/2/4-bit 权重 × int8/fp16 激活；提交模型为 BitNet-3B 三值（**2.44 bit/权重**，986 MB）。

### 2.2 实测证据

| 项 | 结果 |
|---|---|
| 内核自测（m=128 k=3200 n=1 b=2） | **PASS**（zero-in ⇒ zero-out）——真机 arm64 NEON 与模拟器 x86_64 AVX2 **双架构通过** |
| 内核基准（200 次调用） | 模拟器 **1.41 ms（平均 0.0071 ms/次）**；真机 **1.56 ms（平均 0.0078 ms/次）** |
| 端到端吞吐（交付版 App） | 模拟器 **23.35 tokens/s**（首轮 25.01）；真机 **20.39 tokens/s**（256 token 生成） |
| 对反量化基线（同模型同线程，跨平台 CLI 对照） | **2.5–5.9×**（M2-Ultra 2.5–3.4×；树莓派 5 单核 **5.9×**；AGX Orin 5.5×）——**设备算力越受限，优势越大** |
| 模型体积 | 986 MB = 同源 fp16（6.65 GB）的 **1/6.6** |

## 3. 技术核心 ②：端侧记忆调度（链式 KV）

### 3.1 问题

端侧对话中连续提问常带**相同前缀**（多轮对话、模板化提示），常规实现每轮重新 prefill 全部前缀——首字延迟被反复支付。

### 3.2 机制

1. **记忆链**：引擎维护 `kv_tokens`（已解码 token 序列）作为"模型工作记忆"的索引。
2. **最长公共前缀（LCP）**：新请求先与记忆链逐 token 比对，取最长公共前缀 `common`。
3. **分歧裁剪**：`llama_kv_cache_seq_rm(ctx, 0, common, -1)` 精确删除不匹配尾部（命中段不重算）。
4. **增量解码**：仅对 `tokens[common:]` 执行 prefill，随后正常逐 token 解码。
5. **一致性策略**：复用只发生在前缀**逐 token 完全一致**时——不会出现"复用错误上下文"。

### 3.3 成本模型与实测

- 该模型为纯多头注意力（**无 GQA**，loader 日志 `head_count_kv = 32`），每 token 的 KV 读写约 **325 KiB**，是端侧最坏情况；记忆复用同时省下重复前缀的 KV 写入与注意力计算，**收益随对话轮数累积**。
- 实测（同提示连续两轮）：复用 **6/6（模拟器）/ 8/8（真机）**；前缀处理 **239.18 ms → 0.00 ms**；TTFT **239.78 → 0.57 ms**（模拟器）、**248.80 → 1.15 ms**（真机）——**降幅 216×**。
- **部分复用**（追加式提问：前缀同、尾部扩展）：**复用 6 of 13**（前缀 6 复用 + 增量 7 解码）→ 证明是通用 LCP 算法，而非"整轮缓存"的粗糙实现。

## 4. 技术核心 ③：感知调度与系统回收（L2）

### 4.1 机制

应用前后台状态经事件通道进入页面规则引擎；**转后台持续 60 s（滞回阈值）**后释放引擎（内存归还系统）；回前台自动预热重载。60 s 滞回的设计目的：① 避免快速切换造成反复卸载/重载；② **保护链式 KV 记忆链**不被抖动冲掉。策略档位：线程 1/2/4 档、预取（前台驻留预热）、降载（后台释放）；系统通知与温度信号作为可扩展输入预留（规则表驱动，不改引擎）。

### 4.2 实测（同设备、同模型、同后台时长，唯一变量 = 调度开关）

| 状态 | 进程 Pss | 说明 |
|---|---|---|
| 调度开 · 前台（模型已载） | 1370 MB | 基线 |
| 调度开 · 后台 70 s | **71 MB** | **释放 1.30 GB** |
| 调度开 · 回前台 | 1364 MB | 自动重载 1.37 s（加载卡实测） |
| 调度关（对照）· 后台 70 s | **1356 MB** | **不释放** |
| 快速切回（<60 s）×3 | 引擎与 KV 链保持 | 滞回生效（日志实证） |

## 5. 技术核心 ④：采样与输出质量工程（2026-09-30 新增）

自研采样器（不依赖 llama.cpp 采样链）补齐工程化能力：

- **参数**：`top_k = 40 / top_p = 0.95 / temp = 0.8 / repeat_penalty = 1.15（last_n = 64）`
- **实现**：重复惩罚（最近 64 token 的正 logit 除、负 logit 乘）→ top-k → softmax → **top-p 核采样**（按概率降序累积至 0.95）→ 采样；生成循环维护 recent 窗口（提示词 + 已生成）；报告页输出**真实参数**（口径诚实）
- **A/B（同提示）**：
  - 升级前：`…the city of Paris. It is the most visited city in the world attracts millions of tourist every year from every corner of the world and attracts millions of…`（复读退化）
  - 升级后：`the city where all things French are made. From the bistros with crêpes and croissants, to the boutiques brimming with Chanel`（通顺、零复读）
- **成本**：采样耗时 0.44 ms/token，对吞吐口径影响 <0.5%。

## 6. 技术核心 ⑤：双形态与系统服务化

### 6.1 应用级形态（已交付）

ArkTS 原生界面 → NAPI 异步桥 → 静态链接 llama.cpp + LUT 内核的 Native 引擎（双 ABI：arm64-v8a / x86_64）；模型经系统文件选择器导入沙箱（产品级通道）；生成经 threadsafe function 逐 token 回吐（打字机）；四项指标（吞吐/TTFT/加载/峰值内存）实时上屏。

### 6.2 系统服务级形态（预研，载体受限）

**已完成**：SA 类（CreateSession / LoadModel / PrepareWorkspace / WarmKernel / InferTokenBatch / ReleaseSession 六入口 + 感知→QoS 策略接口）+ 注册描述（`profile.json`：LutSystemAbility / libtmac_sa.z.so / run-on startup；`lut_sa.cfg`：class core / on boot / **SA_ID=6901**）+ **qemu 全链路冒烟 PASS**（Create→Load→Prepare→Infer→Release + 前后台信号切换）+ **系统组件脚手架齐备**（`ohos/sa/component/`：`bundle.json` 组件声明、`BUILD.gn`（`install_images=[system]`）、`lut_sa_ability.cpp` samgr 绑定（`REGISTER_SYSTEM_ABILITY_BY_ID(6901)` + `Publish`）、`ILutSa.idl` 对外接口、`sa_profile/` 与 `etc/init/` 配置、**SELinux `.te` 策略与 `file_contexts`**、集成与验证 README）——集成步骤已收敛为「放入 vendor 目录 → 注册子系统 → `build.sh --build-target lut_sa_package` → 刷机」。

**部署载体缺口（实测六条锁）**：零售版 HarmonyOS **不允许第三方注册系统服务**——
① 非 root 且无 `su`（`uid=2000(shell)`）；② SELinux **Enforcing**（真机连 `getenforce` 都拒绝）；③ `/system` 只读、`/system/profile` 与 `/system/etc/init`（第三方 SA 注册描述与启动配置的必经目录）**Permission denied**；④ `/sys_prod` 对 shell 不可写；⑤ 官方工具 `hdc target mount` → **E007100 需 debug 镜像**；⑥ 两套 SDK（DevEco 26.0 / 独立 OH SDK）**均不含 samgr/SystemAbility 头文件**，且无 SA 管理工具。
→ **该形态的正确载体是 OpenHarmony 标准系统镜像/开发板**（把 SA + 注册描述 + SELinux 策略编入镜像，samgr 开机拉起，应用经 `LoadSystemAbility` 调用）；代码与描述文件已就绪，**换载体即可运行**。

### 6.3 应用内服务化上限（如实标注）

`AppServiceExtensionAbility` 仅支持 2in1 设备且需**企业应用专属 ACL 权限**；通用 `ServiceExtensionAbility` 在 API 26 SDK 已不存在 → 零售设备上第三方"服务化"上限 = 后台保活（`BackgroundTasksKit`）。

## 8. 技术核心 ⑦：上游贡献——新版 fork 数值缺口的定位与修复

**现象**：新版 llama.cpp fork（202504_tmac，上游自标 "[WIP] Wrong outputs"）输出退化为 `The capital of France is is is is…`；此前"46.93 tokens/s"实为**内核空转**伪速度（跳过了矩阵乘）。

**定罪**：`get_scales_size` 支持三种口径（`one_scale` → 1 scale/整张量；`has_zero_point` → 每组 (scale+zp)；否则 → **每组 1 个 scale**），而内核分发表 `tbl.cpp` 的 12 个条目**只覆盖两种极端组合且无 else 兜底、不抛错** → 我们所需的组合（BitNet 三值 per-group、无 zp）整段循环空转，`CBits` 恒零 → 输出退化。

**修复**：通用实现 `tbl_g4_int8_float_update_impl<…, ZeroPoint, OneScale>` 的最终 else 分支**早已实现该组合**，只需补 **6 条分发表路由**（bits=2/4 各 3 条 `ZeroPoint=false, OneScale=false`）。补丁入仓：`ohos/patches/tmac-newfork-pergroup-nozp-dispatch.patch`。

**验证**：重建后输出恢复通顺（WSL 复现 ×2）；修复版吞吐 18.66–20.37 tokens/s（同机对照旧 fork 25.10）→ 结论：新版底座更现代但尚未调优，**提交采用旧版**，新版列为复赛后主线（kcfg 调优 + 128 组量化变体）。
